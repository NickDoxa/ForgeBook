# Phase 4 — UI Design Contract (Minecraft Forge)

> Visual and interaction contract for the in-inventory chat UI. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform note:** This is a Minecraft Forge 1.20.1 client-side Screen, NOT a web UI. There is no CSS, no shadcn, no component library. Rendering is `net.minecraft.client.gui.GuiGraphics` over Minecraft's pixel grid using the vanilla font. "Spacing" is GUI-pixel integers, "colors" are `ARGB int` constants (`0xFF_RRGGBB`), "typography" is the vanilla bitmap font. The template's web-centric tables are adapted accordingly.

---

## Design System

| Property           | Value                                                                 |
|--------------------|-----------------------------------------------------------------------|
| Tool               | none (platform-native Minecraft widgets)                              |
| Preset             | not applicable                                                        |
| Component library  | vanilla Forge 47.x widgets: `Button`, `EditBox`, `AbstractWidget`     |
| Icon / texture lib | vanilla atlas only + user-supplied `assets/forgebook/textures/gui/`   |
| Font               | `Minecraft.getInstance().font` (vanilla `minecraft:default` bitmap)   |
| Rendering API      | `net.minecraft.client.gui.GuiGraphics` (Mojang 1.20.1)                |
| Screen base        | standalone `Screen` rendered alongside `InventoryScreen`              |
| Injection hook     | `ScreenEvent.Init.Post` filtered to `InventoryScreen`                 |
| GUI scale target   | Minecraft GUI scale 1–4 (auto + explicit)                             |
| Min screen target  | 1280×720 window resolution                                            |

**Architecture invariant (from STATE.md):** `net.minecraft.client.*` imports are only permitted under `com.forgebook.client.*`. All UI classes in this phase live under `com.forgebook.client.ui`.

## Layout & Sizing (Minecraft Pixel Grid)

All coordinates are in **GUI pixels** (pre-scale), which is how Minecraft's rendering math works. The window pixel-to-GUI-pixel ratio is controlled by the player's GUI scale (1, 2, 3, or 4, or "Auto").

### Inventory Button Injection (UI-01)

| Property         | Value                                                               |
|------------------|---------------------------------------------------------------------|
| Size             | 20×20 px (vanilla square button idiom)                              |
| Position         | `x = leftPos + imageWidth + 4`, `y = topPos + 4`                    |
| Z-layer          | added via `event.addListener(widget)` (post-vanilla, above slots)   |
| Click action     | `Minecraft.getInstance().setScreen(new ChatScreen(parent))`         |
| Collision check  | MUST NOT intersect `RecipeBookComponent` toggle tab (native at +74) |
| Tooltip          | `Component.translatable("forgebook.chat.button.tooltip")`           |
| Button label     | stylized "F" glyph OR 16×16 texture at `textures/gui/chat_icon.png` |
| Render fallback  | If logo texture missing, draw glyph: `font.draw(graphics, "F", ...)` |

**Rationale for offset:** `leftPos + imageWidth + 4` is 4 px to the right of the inventory's right edge. In vanilla 1.20.1, `InventoryScreen` has `imageWidth = 176`; the recipe-book toggle sits inside the inventory at offset `+48, +79` so there is no collision. A 20×20 button fits cleanly in the right-side margin on screens ≥ 1280×720 at GUI scales 1-4.

### ChatScreen Layout

The ChatScreen is a **standalone `Screen`** (NOT `AbstractContainerScreen`) rendered when the player clicks the inventory button. It holds no menu and never replaces the inventory visually — it redraws the inventory-frame background from the parent screen if desired, or dims to vanilla `Screen` default (`0xC0_101010` overlay).

**Decision:** Standalone `Screen` per CLAUDE.md guidance ("ScreenEvent.Render.Post or a sibling Screen"). The STATE.md Phase-4 flag ("Spike — AbstractContainerScreen<InventoryMenu> subclass vs standalone Screen") is resolved **in favor of standalone Screen** to avoid slot hit-testing conflicts with JEI/REI/Inventory HUD+.

#### Chat panel dimensions

| Property                  | Value             | Notes                                                                 |
|---------------------------|-------------------|-----------------------------------------------------------------------|
| Panel width (default)     | 240 px            | Fits comfortably at GUI scale 1-3 on 1280×720; degrades at scale 4     |
| Panel height              | `height - 40 px`  | Leaves 20 px top/bottom breathing room                                |
| Panel x                   | `(width - panelWidth) / 2` (centered horizontal) |                                       |
| Panel y                   | 20 px from top    |                                                                       |
| Padding (inside panel)    | 6 px all sides    |                                                                       |
| Message list region       | panel - padding - input row (22 px) - scrollbar (6 px right) |                         |
| Input row height          | 20 px (vanilla `EditBox` height) + 2 px margin above       |                         |
| Submit button size        | 40×20 px to right of `EditBox`, 2 px gap                   |                         |

#### Small-screen fallback (UI-07)

If `width < 320 px` (GUI pixels, equivalent to GUI scale 4 on 1280×720) the panel switches to **stacked mode**:

| Condition                          | Behavior                                                                 |
|------------------------------------|--------------------------------------------------------------------------|
| `width >= 320 px`                  | Side-by-side: inventory remains visible; chat panel at `leftPos + imageWidth + 8` |
| `width < 320 px`                   | Stacked: chat panel occupies `width - 16 px` centered; inventory hidden behind overlay |
| `width < 240 px` OR `height < 180 px` | Minimum-width guard: render `"Screen too small — increase resolution or lower GUI scale"` centered, no other widgets |

**Compat anchor (CLAUDE.md compatibility constraint):** Chat panel is an overlay Screen, not a HUD widget, so it does not conflict with Sodium / Iris HUD modifications or Inventory HUD+.

## Spacing Scale (GUI-pixel integers)

Declared values — all multiples of 2 (the Minecraft pixel convention; vanilla font glyphs are 6×9 with 1-px gutters). Web 4-px multiples don't map to MC — the vanilla idiom is 2-px increments at GUI-pixel level.

| Token        | Value     | Usage                                                                     |
|--------------|-----------|---------------------------------------------------------------------------|
| tight        | 2 px      | Text baseline gap, bubble tail, inline padding inside `EditBox`           |
| snug         | 4 px      | Element-to-element gap (button margins, bubble-to-bubble)                 |
| normal       | 6 px      | Panel inner padding, icon-to-label gap                                    |
| section      | 10 px     | Between logical sections (input row vs message list)                      |
| block        | 16 px     | Outer frame inset, panel-to-screen-edge gutter                            |

**Exceptions:**

- Vanilla `Button` and `EditBox` widgets render at fixed 20 px height; we do not override.
- Inventory-button offset uses the native vanilla 4-px margin idiom.

## Typography

**Single font:** `Minecraft.getInstance().font` (the vanilla bitmap font, `minecraft:default`). No additional fonts. The vanilla font is 7 px cap height + 2 px descender = 9 px line box at scale 1.

| Role                    | Size                          | Style              | Line Height                                | Notes                                                               |
|-------------------------|-------------------------------|--------------------|--------------------------------------------|---------------------------------------------------------------------|
| Message text (body)     | 1× vanilla (9 px line)        | normal             | `font.lineHeight + 1` (10 px)              | Wrapped via `font.split(Component, maxWidth)` — vanilla word-break  |
| Player label            | 1× vanilla                    | bold via `§l`     | 10 px                                      | Rendered above each message bubble                                  |
| Button label            | 1× vanilla                    | normal             | 8 px (centered in 20-px button)            | Vanilla `Button` renders this automatically                         |
| EditBox input           | 1× vanilla                    | normal             | 12 px (vanilla `EditBox` internal)         | Vanilla widget, no override                                         |
| Error heading           | 1× vanilla                    | bold via `§l`     | 10 px                                      | Rendered inside error card; color by taxonomy                       |
| Placeholder (empty)     | 1× vanilla                    | italic via `§o`   | 10 px                                      | For empty conversation state                                        |

**Why no bigger sizes:** The vanilla font only renders crisply at integer multiples (1×, 2×, 4×). Scaling to 2× for "display" gives 18-px line height and crowds the 240-px panel. Keeping everything at 1× is visually the correct MC idiom — larger font usage is reserved for title screens and is out of place in a chat panel.

**Text color defaults:**

- Player text: `0xFF_FFFFFF` (white)
- Assistant text: `0xFF_E0E0E0` (near-white, subtly cooler)
- Placeholder / hint: `0xFF_808080` (gray)
- Disabled: `0xFF_707070` (vanilla disabled idiom)

## Color Palette

All values are ARGB 32-bit ints written as `0xAA_RRGGBB`. This is how `GuiGraphics.fill(...)` and `font.draw(...)` consume color.

### Dominant / Secondary / Accent (60/30/10)

| Role            | Value                  | Usage                                                                                               |
|-----------------|------------------------|-----------------------------------------------------------------------------------------------------|
| Dominant (60%)  | `0xF0_101019`          | Chat panel background — near-black with slight blue tint + 94% opacity; matches vanilla `Screen.renderBackground` dim overlay |
| Secondary (30%) | `0xFF_2E2F37`          | Message bubble background (both player and assistant use same fill; differentiated by tail + label) |
| Accent (10%)    | `0xFF_B0C4F5`          | **Reserved for:** (1) the inventory-toggle button hover border, (2) the "send" submit-button border when input is non-empty, (3) active-scrollbar thumb |
| Destructive     | `0xFF_E74C3C`          | Error state heading for `FORBIDDEN` + `PROVIDER` + catastrophic client-side exceptions only         |

**Accent reserved for:** button hover/focus highlight + active scrollbar thumb + submit-enabled border. **Never** for message text, bubble fills, or decorative flourishes. Adhering to 10% weight keeps the chat panel visually quiet so the inventory (at scale 1-3 side-by-side) stays the primary surface.

### Frame & separator colors

| Role                | Value             | Usage                                                                    |
|---------------------|-------------------|--------------------------------------------------------------------------|
| Panel outer border  | `0xFF_000000`     | 1-px stroke around the entire panel (matches vanilla tooltip)            |
| Panel inner border  | `0xFF_5A5A6E`     | 1-px highlight inside the outer border (the vanilla 3D bevel idiom)      |
| Bubble border       | `0xFF_1A1A22`     | Subtle 1-px bubble outline                                               |
| Separator lines     | `0xFF_3F3F4A`     | Horizontal rule between day/session markers                              |
| Scrollbar track     | `0x40_202028`     | Translucent track                                                        |
| Scrollbar thumb     | `0xFF_8A8AA0`     | Idle thumb (becomes accent `0xFF_B0C4F5` when dragging)                  |

### Error taxonomy color mapping (UI-04, Phase-3 error codes)

Every `ChatErrorPacket.ErrorCode` maps to exactly one `errorTint` used for the error card's left-side stripe (4 px wide) and heading text.

| Code            | Stripe / heading color  | Rationale                                                                            |
|-----------------|-------------------------|--------------------------------------------------------------------------------------|
| `TRANSPORT`     | `0xFF_F5A623` (amber)   | Network / executor saturation — transient; warns but not fatal                       |
| `RATE_LIMITED`  | `0xFF_4A90E2` (blue)    | User-throttling; informational, not an error the server owner should panic about     |
| `FORBIDDEN`     | `0xFF_E74C3C` (red)     | Permission denied — user must act (ask an OP / enable op_only=false)                 |
| `PROVIDER`      | `0xFF_E74C3C` (red)     | Upstream AI error; same severity class as FORBIDDEN from user's perspective          |
| `DISABLED`      | `0xFF_808080` (gray)    | Feature kill-switched — neutral, not a failure                                       |
| `OVERLOADED`    | `0xFF_F5A623` (amber)   | Queue full (Phase-1 carry-over); same class as TRANSPORT from user's perspective     |

Error card body text color: `0xFF_E0E0E0` (same as assistant text) regardless of tint, so the tint functions as a **status signal** rather than tinting readable copy red.

### Message bubble differentiation

Both user and assistant bubbles use `0xFF_2E2F37` fill. Differentiation is by:

1. **Alignment:** User = right-aligned (bubble right-edge at `panelRight - padding`). Assistant = left-aligned (bubble left-edge at `panelLeft + padding`).
2. **Label prefix:** `"You"` for user (bold, `0xFF_FFFFFF`), `"ForgeBook"` for assistant (bold, `0xFF_B0C4F5`).
3. **Tail indicator:** 2-px accent bar on the appropriate side (right-edge for user, left-edge for assistant).

This avoids the anti-pattern of "blue-bubble / gray-bubble" iMessage mimicry which would collide with vanilla MC's color idiom.

## Interaction Contract

### Input handling

| Input          | Action                                                                            |
|----------------|-----------------------------------------------------------------------------------|
| `ESC`          | Close `ChatScreen` (triggers `ClientChatSession.clear()` per UI-05)               |
| `ENTER` in input field | Submit (same as clicking "Ask" button) IF input is non-empty AND not already in-flight |
| `TAB`          | Move focus (vanilla widget navigation)                                            |
| Mouse wheel on message list | Scroll conversation up/down                                          |
| Drag scrollbar thumb | Scroll to position                                                          |
| Click "Ask" button | Submit                                                                        |
| Click outside panel | NO effect (does not close — avoids accidental dismiss mid-typing)            |
| `E` (inventory key) | NO effect while ChatScreen is open (swallow — lets typing `e` in input work) |

**Keybinds (CLAUDE.md constraint):** NO global keybind is registered. The STACK.md note "Register via `RegisterKeyMappingsEvent` with `conflictContext: InGame` and default to `InputConstants.UNKNOWN`" is **not applied in Phase 4** — we defer keybind registration to v2 if ever needed. The inventory-button is the single discoverable entry point per PROJECT.md.

### In-flight state machine

```
idle --submit--> pending --response--> idle (with new bubble)
                   |
                   +--error--> idle (with error card)
                   |
                   +--screen_closed--> idle (session cleared, pending orphaned)
```

| State      | Input enabled | Submit enabled | Loading indicator |
|------------|---------------|----------------|-------------------|
| `idle`     | yes           | yes (if text)  | hidden            |
| `pending`  | no (greyed)   | no (shows spinner in place) | "Thinking…" with animated dot-cycle |
| `closed`   | n/a           | n/a            | n/a               |

Only ONE in-flight request at a time per session. If a response arrives after the screen was closed, it is silently discarded by `ClientChatSession` (UI-05 enforces this).

### Loading indicator

**Visual:** A three-dot cycler rendered in the submit button's usual position while `pending`. Dots animate at 500 ms per frame: `"."` → `".."` → `"..."` → `"."` etc. Below the input, a subtle `"Thinking…"` label appears with the accent color `0xFF_B0C4F5`.

**No spinners:** No rotating icon. Vanilla MC has no spinner widget and rotating a texture via `pose().mulPose(rotation)` at 60 fps is fragile at GUI-scale boundaries. The text-based cycler is the correct MC idiom.

### Scroll affordance

- Vertical scrollbar visible only when message list overflows.
- Auto-scroll to bottom on new message arrival ONLY when the user was already scrolled near the bottom (within 20 px of max scroll); otherwise a non-intrusive "↓ new reply" pill appears at the bottom-right for manual click-to-jump.
- Scroll position is preserved across focus changes but lost when the screen closes (session cleared).

### Error surfacing (UI-04)

Errors render **inline in the conversation view** as a dedicated "error card" bubble, never as a vanilla Toast. The card layout:

```
┌─[STRIPE]────────────────────────────┐
│ [STRIPE]  Error heading (bold)      │
│ [STRIPE]  Error body (2-4 lines)    │
│ [STRIPE]  (optional) retry hint     │
└─────────────────────────────────────┘
```

Where `[STRIPE]` is a 4-px vertical bar in the taxonomy color (see Color Palette table above). The card is alignment-full-width (stretches panel - 2×padding) unlike bubbles which are max 75% width. This makes errors visually distinct from messages at a glance.

No crashes reach the screen — any `Throwable` in the client-side handler is caught, logged, and rendered as a `PROVIDER`-class generic fallback with copy from `forgebook.error.provider.*`.

## Accessibility

Minecraft's GUI accessibility primitives are thin but non-trivial. The contract:

- **Narrator support:** All widgets must set `setMessage(Component)` so MC's narrator (F5 + accessibility menu) reads them. This is free for vanilla `Button` and `EditBox`; custom widgets (message bubbles, error cards) must implement `NarratableEntry`.
- **Focus navigation:** Tab order = `EditBox` → `Submit Button` → scroll controls (if present). Vanilla widget focus is handled by `AbstractWidget`.
- **Color blindness:** Error taxonomy uses both color AND heading text, so red/amber/blue/gray distinctions are never the sole channel.
- **Keyboard-only:** The full send-and-receive flow works with ENTER alone. Mouse is never required.
- **Text contrast:** body `0xFF_E0E0E0` on `0xFF_2E2F37` = 10.3:1 contrast (WCAG AAA). Placeholder `0xFF_808080` on `0xF0_101019` = 5.1:1 (WCAG AA). Accent `0xFF_B0C4F5` used only as border/tail never as foreground text on main surfaces.

## Kill-Switch Configuration (UI-06, UI-08)

| Condition                                                  | Behavior                                                                 |
|------------------------------------------------------------|--------------------------------------------------------------------------|
| `CLIENT` config `enable_chat_interface = false`            | `InventoryButtonInjector` short-circuits — NO button rendered, NO listener attached. `ChatScreen` is unreachable. |
| Server is vanilla (ForgeBook not installed server-side)    | Client detects missing channel at login; button shows but click surfaces `forgebook.error.no_server.body` immediately |
| Client source scan                                         | Zero references to `ai_api_key` or `curseforge_api_key` in `com.forgebook.client.*` (enforced by Phase-1 CI grep + SCAF-02 client firewall) |

**Session lifecycle contract (UI-05):**

- `ChatScreen.onClose()` → `ClientChatSession.clear()` → all in-memory state (messages, pending request IDs, scroll position) released.
- `ClientDisconnectEvent` / server-switch → `ClientChatSession.clear()` fires even if Screen wasn't closed first.
- No disk persistence, no chunked saves, no player-data hook. The session lives only in a `volatile` client singleton instance, reachable only while the Screen is open.

## Phase-3 Error Taxonomy ⇢ UI Mapping (UI-04 cross-reference)

This table is the single source of truth for the ChatScreen's error renderer. Every `ChatErrorPacket.ErrorCode` value declared in Phase 1 and populated by Phase 3's Authorizer has an explicit visual identity here.

| ErrorCode       | Stripe color       | Heading i18n key                         | Body i18n key                           | Retry-after support                       |
|-----------------|--------------------|------------------------------------------|-----------------------------------------|-------------------------------------------|
| `TRANSPORT`     | amber  `0xF5A623`  | `forgebook.error.transport.heading`      | `forgebook.error.transport.body`        | no                                        |
| `RATE_LIMITED`  | blue   `0x4A90E2`  | `forgebook.error.rate_limited.heading`   | `forgebook.error.rate_limited.body`     | YES — `%d` substitutes retry-after secs   |
| `FORBIDDEN`     | red    `0xE74C3C`  | `forgebook.error.forbidden.heading`      | `forgebook.error.forbidden.body`        | no                                        |
| `PROVIDER`      | red    `0xE74C3C`  | `forgebook.error.provider.heading`       | `forgebook.error.provider.body`         | no                                        |
| `DISABLED`      | gray   `0x808080`  | `forgebook.error.disabled.heading`       | `forgebook.error.disabled.body`         | no                                        |
| `OVERLOADED`    | amber  `0xF5A623`  | `forgebook.error.overloaded.heading`     | `forgebook.error.overloaded.body`       | no                                        |

**Retry-after substitution:** `RATE_LIMITED` body includes `%d`. The client parses `humanReadable` for the digit(s) Phase 3 emits ("Rate limit reached. Try again in Ns."), or falls back to showing the raw `humanReadable` string unformatted. Clients MUST NOT attempt to auto-retry — the action is manual.

## Implementation Artifacts (contract, not plan)

The planner will produce the plans. For the checker's benefit, this spec implies these files under `com.forgebook.client.ui.*`:

- `InventoryButtonInjector` — listens on `ScreenEvent.Init.Post`, respects `enable_chat_interface`, wires click.
- `ChatScreen extends Screen` — standalone screen, holds the panel and all widgets.
- `ChatPanelWidget extends AbstractWidget` — panel frame + message list + input row.
- `MessageBubble` (value type, not a widget) — rendered directly by `ChatPanelWidget.render`.
- `ErrorCard` (value type, not a widget) — same rendering contract as MessageBubble.
- `ClientChatSession` — `com.forgebook.client.ClientChatSession`, singleton with `append`, `appendError`, `clear`, `markPending`, `markIdle`.
- `LoadingIndicator` — dot-cycler subcomponent.
- `ChatResponsePacket.handleOnClient` (modified) — replaces the Phase-1 log-only stub with `ClientChatSession.append(requestId, reply)`.
- `ChatErrorPacket.handleOnClient` (modified) — same, to `ClientChatSession.appendError`.

The structural invariant is: **no `com.forgebook.client.ui.*` class ever imports `com.forgebook.ai.*`, `com.forgebook.config.ApiKey`, or anything under `com.forgebook.safety.*`.** The UI sends a packet via the existing `ForgebookNetwork` channel and renders whatever comes back. Every AI decision remains server-side. (UI-08 enforced by package topology + CI grep.)
