<objective>
Insert the SAFE-06 authorization precheck into `ChatRequestHandler.handleForTest` so spoofed or disabled CHAT_UI packets are rejected on the NETWORK THREAD before they reach `AiExecutor.submit`. This prevents a malicious client from burning executor queue slots or provider budget by sending packets with forged `hasPermissions(2)` states. The check runs on the network (Netty) thread, emits `ChatErrorPacket` via the existing responder sink, and calls `RequestAuditLogger.logDenied`.

Purpose: SAFE-06 is the core defense against client-side spoofing. Authorizer re-reads `player.hasPermissions(2)` server-side — the client cannot lie about its OP status. Placing the check BEFORE `AiExecutor.submit` (rather than inside the submitted task) matters because the AiExecutor queue is a finite resource (ArrayBlockingQueue(64)) — allowing spoofed packets to enqueue would let a single attacker DOS the queue even if their requests were ultimately denied.
Output: 10-line surgical insertion in `ChatRequestHandler.handleForTest` + unit test exercising the precheck. The existing test (`ChatEchoGameTest` from Phase 1) continues to pass because Allowed packets follow the untouched Phase 2 code path. Plan 03 already updated the `AiDispatcher.dispatch` call site to use `DispatchContext` — this plan confirms and wires the RequestKind.CHAT_UI parameter.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → ChatRequestPacket | The client serializes the packet; the server cannot trust `pkt.message()` content OR any client-side permission claim. `sender` is set server-side by Forge from the authenticated connection. |
| ChatRequestHandler → AiExecutor | Executor queue is a bounded shared resource (64 slots). Uncontrolled submission is a DOS vector. |
| ChatRequestHandler → AiDispatcher | Post-auth entry point; Authorizer gate upstream guarantees only allowed requests pass. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05-01 | Spoofing | Client forges `hasPermissions(2)` via a modified client jar | mitigate | `Authorizer.authorize` re-reads `sender.hasPermissions(2)` from the authenticated `ServerPlayer` — which reads from the server's op list, not the client payload. Forged permissions are ignored by construction. |
| T-03-05-02 | Tampering | Attacker modifies `pkt.message()` to include `\u0000` or control characters to confuse downstream | accept | Phase 2 already trims + length-checks message in ChatRequestPacket encode. Auth layer is content-agnostic — only checks permissions and rate limit. Downstream content sanitization is AiDispatcher's responsibility (unchanged). |
| T-03-05-03 | Repudiation | Operator needs audit trail of DENIED packets to identify spoofing attempts | mitigate | `RequestAuditLogger.logDenied(uuid, CHAT_UI, code, startNanos)` fires on every denial. Log line includes UUID (accountable identity) and code (reason). SAFE-04 satisfied for the denial path. |
| T-03-05-04 | Denial of Service | Attacker sends 1000+ spoofed packets to exhaust AiExecutor queue (ArrayBlockingQueue(64)) | mitigate | SAFE-06 precheck runs BEFORE `AiExecutor.submit`.
